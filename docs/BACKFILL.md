# 過去の未処理メールを再処理する

通常の検索期間を過ぎた未処理メールは、`SYNC_START_DATE` と `SYNC_END_DATE` で回収できます。形式は `YYYY-MM-DD`、両端の日付を含む日本時間です。例えば開始日・終了日が同じなら、その日の00:00以上、翌日の00:00未満を検索します。片側だけの指定も可能ですが、復旧時は両方を指定して期間を限定してください。

期間指定は `SYNC_PERIOD_HOURS` / `SYNC_PERIOD_DAYS` より優先します。通常の時間指定の動作は変わりません。Gmailの検索ページをすべて読み、メールIDを重複排除してGmailの受信時刻（`internalDate`）の古い順に処理します。[Gmailは日付文字列をPSTとして解釈する](https://developers.google.com/workspace/gmail/api/guides/filtering)ため、期間検索には秒単位の時刻を渡し、取得後にも境界を検証しています。

## 実行前

- 対象モデルが利用でき、架空メールで抽出できることを確認する。`OPENAI_MODEL` の説明はREADMEを参照。
- 通常ジョブと別の手動実行を止め、すでに動いている実行の終了を待つ。処理済みラベルは排他ロックではないため、同時に書き込むと重複する可能性がある。
- カレンダーをバックアップし、最初は短い期間で結果を確認する。
- 必要な認証情報を設定する。キー・トークン・メール本文・予約番号・実環境の識別子をIssueや実行例へ貼らない。

## ローカル実行

通常の設定を保存し直さず、このプロセスだけ日付を上書きします。以下は架空の日付です。

```bash
SYNC_START_DATE=2030-01-01 SYNC_END_DATE=2030-01-02 uv run python -m src.main
```

## Cloud Run Jobs

以下の `PROJECT_ID`、`REGION`、`SCHEDULER_NAME`、`JOB_NAME` を実環境に合わせます。Schedulerが元々停止中だった場合は、最後に再開しません。

```bash
gcloud scheduler jobs pause SCHEDULER_NAME --project=PROJECT_ID --location=REGION

# 実行中の通常ジョブが完了し、他の手動実行がないことを確認してから実行
gcloud run jobs execute JOB_NAME \
  --project=PROJECT_ID --region=REGION \
  --update-env-vars=SYNC_START_DATE=2030-01-01,SYNC_END_DATE=2030-01-02 \
  --wait

# 下記の確認を終え、通常実行に戻せる場合に再開
gcloud scheduler jobs resume SCHEDULER_NAME --project=PROJECT_ID --location=REGION
```

`jobs execute --update-env-vars` はその実行だけの上書きです。`jobs update --set-env-vars` で日付を永続設定しないでください。実行権限に加え、Cloud Runの実行時上書き権限が必要です。

タイムアウト内に収まらない場合は日付範囲を分割し、各実行の完了を待って次へ進みます。開始日・終了日は両方を含むため、例えば1〜2日、3〜4日のように分割できます。同じ日を再指定しても成功ラベル付きのメールは除外されます。

## 再処理時の保護と停止条件

- 処理済みラベル付きメールを再登録しません。成功・後続メールにより置き換え済みと確認できたメールだけに成功ラベルを付けます。
- 書き込み前に対象メールを抽出し、同じ事業者・予約識別子に対する後続の処理済みメールを読み取り照合します。この照合には終了日を適用しません。カーシェアでは後続の処理済み変更・取消がある古いメールを書き込まず、置き換え済みとして処理を完了します。確認番号と予約番号は種類を区別して照合します。
- 航空券で同じ予約の後続処理済みメールがある場合は、片道の案内を予約全体の置換と推定せず、書き込み・成功ラベル付与の前に停止します。便ごとの登録状態を手動確認してください。通常の航空券更新でも便名・経路・出発時刻を照合し、メールに記載のない便は削除しません。便の対応が曖昧な場合も停止します。
- 照合には追加のGmail取得・モデル呼び出しが発生します。予約識別子がない、処理済みメールを解析できない等の場合は、状態を推測せず書き込み前に失敗します。手動で内容を確認してください。
- 既存イベントの事業者は記録済みの送信元ドメインで確認します。旧イベントでは元メールを読み取り確認します。元メールを参照できない場合は書き込みを止めます。
- 予約変更は既存イベントを更新してから余剰イベントを削除します。API失敗・解析失敗・登録/更新/取消の一部失敗は正常スキップにせず、終了コードを非ゼロにします。失敗メールには成功ラベルを付けません。

## 完了確認

実行基盤の成功表示だけでなく、アプリの件数集計・失敗件数・カレンダーの最終状態を確認します。予約→変更→取消の順序、取りこぼし、重複がないことを確認してください。取消済み予約が復活していないことも確認します。

エラー検索はアプリの `severity` または `jsonPayload.level` を使えます。対象メールが0件の場合はモデル呼び出しも0回なので、その実行だけではモデルや書き込みの動作確認にはなりません。失敗があれば原因を解消して同じ範囲を再実行し、成功分のラベルを一括で外さないでください。
